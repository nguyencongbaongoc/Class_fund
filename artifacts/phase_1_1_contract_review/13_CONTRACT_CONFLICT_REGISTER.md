### Conflict 1: Idempotency Key Stability Across Retries (Critical — BLOCKED)
- Source: `08_FINANCIAL_IDEMPOTENCY_AUDIT.md` (full audit; `ledger.py` lines 39–57; `post_transaction()` lines 59–118; `verify_and_post_from_ai()` lines 172–241).
- Conflict: Phase 1 design (`08` / `11` / `03`) proposes new format `msg_{message.id}_attempt_{retry_count}`; this key changes when `retry_count` changes; `check_idempotency()` (line 43–51) uses `key` as lookup; changed key → `None` result; fingerprint (same) does not include `message.id` or `retry_count`; `post_transaction()` falls back to DB `duplicate` check (`WITH FOR UPDATE`); `409` raised (`Duplicate transaction code`); `post_revert()` has independent fingerprint (`revert` + `original.id` + `reason`) — not affected by `retry_count`, but revert is separate operation.
- Impact: Financial posting remains safe (DB constraint prevents duplicate); message retry loop may become unstable (message fails to receive `transaction_id`; retry increments; no clean existing response returned; potential infinite retry loop or `failed` after max retries rather than returning existing transaction).
- Evidence: `ledger.py` fingerprint definition (line 39); `check_idempotency()` logic (line 43–51); `post_transaction()` `duplicate` check (line 80–86); `verify_and_post_from_ai()` `existing_tx` check (line 177–179); `post_transaction()` `IntegrityError` rollback (line 114–117); `verify_and_post_from_ai()` rollback and `DUPLICATE` update (line 236–241); `11_FINANCIAL_GATEKEEPER.md` contract (references `idempotency_key` format); `08_LOCAL_WORKER.md` retry design (`reset_to_pending()` with `retry_count` increment); `03_MESSAGE_CONTRACT.md` (`retry_count` definition).
- Severity: HIGH (reliability/stability, not financial integrity — DB protects against duplicate transactions).
- Status: BLOCKED (design conflict; requires Phase 2 resolution; source not modified).
- Proposed Resolution (documentation only, `08_FINANCIAL_IDEMPOTENCY_AUDIT.md`): Option A (modify fingerprint to include `message.id`; stable key `msg_{message.id}`); Option B (rely on DB `duplicate` check; add `message.transaction_id` pre-check before retry); Option C (document conflict; resolve in Phase 2).
- Owner: Minh (financial gatekeeper contract) + Ngọc (idempotency format contract) + coordination with `08` audit document.

### Conflict 2: Recall Authorization Security Gap (Critical — BLOCKED)
- Source: `12_RECALL_SAFETY.md` (token design only); `19_GUEST_CHAT_PHOTO_MESSAGE_RECALL_AUDIT.md` (Phase 0: critical — zero authorization; no token; no ownership check); `05_AUTH_RLS_SECURITY_REVIEW.md` (token mechanism unimplemented); `03_MESSAGE_CONTRACT.md` (`public_code` not authorization); `11_FINANCIAL_GATEKEEPER.md` (message-to-transaction link requires `message.id` linkage — design only; no source).
- Conflict: Design proposes secure recall (`public_code` excluded; private token; hash stored); source code has no token generation (`messages` table has `recall_token_hash` column in schema design but no `INSERT` logic creates it); no authorization endpoint exists (`revert_transaction` in `AppContext` has no authorization; `post_revert()` requires `actor_id` but no `message.id` authorization); message-level `recalled` state transition is design-only (`12`); source `post_revert()` checks `original.id` and `actor_id` (backend authorization), not message-level authorization.
- Impact: Recall mechanism is incomplete at source level; security authorization gap remains (Phase 0 critical finding not fully resolved by Phase 1 design).
- Evidence: `12` token/hash design (`recall_token_hash` column); `03` (`public_code` contract excludes authorization); `05` (security review: `BLOCKED` — authorization mechanism unimplemented); `08` audit (`BLOCKED` — no authorization endpoint in adapter/worker); `11` (`post_revert()` requires `actor_id`; no `message.id` authorization parameter); `19` Phase 0 audit (`revertTransaction` mock has zero authorization; no session; no token).
- Severity: CRITICAL (security authorization gap — not resolved by design alone).
- Status: BLOCKED (design contract exists; authorization mechanism requires Phase 2 source implementation).
- Proposed Resolution (documentation only): Confirm token generation endpoint; confirm `message.id` linkage to `post_revert()`; confirm authorization endpoint uses token hash (not `public_code`); document in `12` that authorization source implementation is a Phase 2 prerequisite.

- Conflict: `verify_and_post_from_ai()` (`ledger.py` lines 172–241) currently checks `upload.id` (`existing_tx`), `upload.status` (`REJECTED`, `DUPLICATE`), `upload.id` (`DUPLICATE` DB check), and `message.id` is not passed as parameter (new design proposes it). The design (`11`) proposes passing `message.id` and checking `message.status = 'recalled'` before posting. Source `verify_and_post_from_ai()` does not currently accept `message.id`; no `message.status` check exists.
- Impact: Recall-before-post behavior (design contract) requires new parameter and new check in `post_transaction()` or `verify_and_post_from_ai()`; source modification blocked in Phase 1.1; design contract confirms requirement but implementation unverified.
- Evidence: `ledger.py` (`verify_and_post_from_ai()` parameters — `upload`, `result`, `account`, `actor_id`, `idempotency_key`; no `message.id`); `11` (design proposes `message.id` linkage; `message.status` check before posting); `12` (recall before post design); `08` audit (before posting: `message.status` check required; design confirms; source missing).
- Severity: HIGH (functional gap — recall before posting is a critical safety feature; design contract confirms it; source implementation required for Phase 2).
- Status: BLOCKED (design contract confirms requirement; source modification blocked for Phase 1.1; must be Phase 2 prerequisite).
- Proposed Resolution (documentation only): Confirm `message.id` linkage and `message.status` check must be added to `verify_and_post_from_ai()` (or adapter/work-flow) in Phase 2; document this as entry criterion in `14_PHASE_2_ENTRY_CRITERIA.md`.
